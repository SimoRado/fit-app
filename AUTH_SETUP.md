# Fitapp authentication setup

Fitapp keeps its existing Clerk application, Convex provider, account-specific SQLite files, RevenueCat customer identity, and cloud-backup consent. Email/password, recovery, and email-code verification continue to use `@clerk/expo` 4.15.0.

## Google through Clerk-managed browser OAuth

The Welcome, Sign In, and Sign Up screens call Clerk `useSSO().startSSOFlow({ strategy: 'oauth_google' })`. The browser return URL is derived from the configured `betterday` scheme and fixed `oauth-callback` route: `betterday://oauth-callback`. Expo AuthSession also generates its native return URL for comparison; the stable app URI is passed to Clerk so a Metro host address cannot enter the allowlist requirement. Clerk creates or finds the Google-linked account. After Clerk returns a session ID, the app calls `setActive`; Expo Router's protected screens then navigate through the existing profile check. A new account sees fitness onboarding; a returning account with a local profile skips it. No Google password or separate email OTP is requested.

The browser flow uses Clerk's existing Google social connection. It does **not** need `EXPO_PUBLIC_CLERK_GOOGLE_WEB_CLIENT_ID` or `EXPO_PUBLIC_CLERK_GOOGLE_ANDROID_CLIENT_ID` in Fitapp, and no Google Cloud credentials are stored in the Expo bundle. If Clerk's shared development Google credentials are enabled for the selected development instance, no new Google Cloud client is needed. The Clerk dashboard must allow the actual return URL (`betterday://oauth-callback`) under **Native applications → Allowlist for mobile SSO redirect**. Its exact connection/allowlist state was not independently readable through the available browser automation, so verify it before device testing.

For reliable redirect testing, install a development build with the `betterday` scheme and the `expo-web-browser` plugin. Expo Go cannot register this app-specific return scheme. Android package remains `com.bettereveryday.fitness`. The previously identified local debug SHA-1 `04:C7:C0:2F:F8:CD:68:A4:36:F0:8F:9D:55:0B:99:AB:32:39:49:16` matters only if switching back to **native** Google sign-in; it is not a prerequisite for this Clerk-managed browser OAuth flow. The existing EAS development profile builds an Android APK and can be used for an iOS development build after Apple signing is configured.

### Android diagnosis and retest

RevenueCat's installed SDK prints “Expo Go app detected. Using RevenueCat in Browser Mode” only when its Expo Go runtime marker is present without the native purchases module. The local React Native DevTools window was also titled `Expo Go`, providing a second indication of the prior runtime. That phone log is evidence the app ran in Expo Go even though the Metro terminal said “Using development build”; the latter describes Metro's launch mode. Expo Go does not own the `betterday` scheme, so Clerk's browser return cannot reliably reach Fitapp. The Google button remains disabled in Expo Go with an explanation; it is enabled in an idle native build. The RevenueCat preview check uses the same runtime classification so it does not mistake a real development build for Expo Go.

With USB debugging enabled and the Redmi connected, verify it appears in `adb devices`. Check for the existing package with `adb shell pm path com.bettereveryday.fitness` before installing. If Android reports a signature conflict, stop: replacing the installed package could require uninstalling it and would erase its local data. Otherwise run `npx expo run:android --device` in this project to build and install the native Fitapp app. Then run `npx expo start --dev-client --clear`, open the **Fitapp / Better Every Day** app icon on the phone (not Expo Go), and connect it to Metro. The development log should show `[Fitapp Google OAuth] runtime` with `kind: 'native-build'`; the RevenueCat Expo Go log should be absent. Use `adb shell am start -a android.intent.action.VIEW -d betterday://oauth-callback com.bettereveryday.fitness` only as a standalone deep-link smoke test when no OAuth attempt is in progress. It should open Fitapp's harmless callback screen; then return to Welcome. Try Continue with Google. The safe diagnostic sequence is `button press`, `initiation`, `browser completion` with `browserResult: 'success'` and `createdSession: true`, `session activation started`, `session activation completed`, then `Clerk auth state` with `signedIn: true` and `protected navigation` to dashboard or onboarding. The logs omit user IDs, tokens, codes, and full URLs.

If the browser returns but `createdSession` stays false, inspect the non-secret status and ensure `betterday://oauth-callback` is allowed in the **existing Clerk development instance** Redirect URLs. If the browser never returns, confirm the installed package is `com.bettereveryday.fitness` and was rebuilt after adding the scheme. The generated Expo Android manifest has a `betterday` intent filter, but no phone was connected through ADB to verify an installed manifest or actual callback. Test cancellation, closing the browser, new-user onboarding, returning-user dashboard, app restart, sign-out, and sign-in again on the native build. Android device testing remains pending.

## Apple and email

Apple now uses Clerk's native Apple hook on configured iOS development builds and Clerk browser OAuth on configured Android development builds. Both stay disabled until their Clerk configuration is confirmed. See [APPLE_AUTH_SETUP.md](APPLE_AUTH_SETUP.md) for the current implementation and platform-specific setup steps. Email registration, verification, sign-in, and password recovery are unchanged.

## Verification limits

The generated Android manifest was inspected through `npx expo config --type introspect --json` and includes a `betterday` intent filter for the configured Android package. TypeScript, lint, 75 automated tests, and Android JavaScript export passed. Expo Doctor passed 19 of 20 checks; it found existing SDK version mismatches for `react-native-safe-area-context`, `expo`, `expo-notifications`, and `expo-router`. These packages were left unchanged for this focused fix.

`adb devices -l` returned no attached device. No Google login, installed-app deep link, Clerk session activation, app restart, or account switch was completed on a phone in this phase. The Clerk Google connection was reported enabled by the project owner; its redirect allowlist still requires dashboard confirmation. Browser automation could not safely identify the current browser page and stopped before opening the dashboard. A successful JavaScript export does not prove live OAuth.
